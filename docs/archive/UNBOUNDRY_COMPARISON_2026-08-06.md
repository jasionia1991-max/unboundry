## 2. 生成链路审计结论

### 2.1 Unboundry 的机制

- 提交即返回 `taskId`（`result.ids[0]`），节点写入 `taskInfo {status: pending, taskId}`；
- 前端轮询 `taskInfo.status`（排队中/等待中 → 运行中 → 已完成/失败），完成后把
  `generated_images/videos/texts/audios` 写回节点；
- 前端没有任何“平台连接配置锁 / 画布保存完才能生成”的门禁；并发排队在服务端；
- 整组执行：`filterExecutableNodes` → 余额预检 → `buildDependencyGraph` →
  `getLayeredExecutionOrder` → 逐层执行；**同层 `Promise.all` 并行提交，跨层串行**；
  层间先停 1s，再每 5s 轮询该层节点 `taskInfo`（最长 500s），全部 completed 才进下一层；
- 任一节点失败 → 整组停止 + “整组执行失败” toast；跳过 → 停止不报错；可取消；
- 错误处理：提交失败按错误码映射（10006 余额不足→弹钱包、10007 组织额度、
  字段类错误码字典）；轮询失败 → 节点 `pollingPaused + pollFailCount`，
  “任务状态查询失败，点击重试重新检查”，可恢复轮询；
- 刷新/异常恢复：`getLatestTasksByNodes` 按 nodeId 找回任务；
- 任务完成广播 `tapflow-plugin:generation-complete`（结果 URL + 源节点），
  用于下游输入更新与历史缓存失效，不自动触发下游生成。

### 2.2 我们（Lumino/Unboundry 复刻）的机制

- `ensureGenerationTask`：本地幂等键（localStorage + 内存）→ 幂等查询 →
  preflight（输入/额度/连接）→ POST → 响应丢失时按幂等键找回，防重复付费；
- 服务端持久任务队列（queued/running/retrying/recovering/success/failed/cancelled），
  `waitForGenerationTask` 1s 轮询；
- 整组执行：分层、层内并行、跨层串行、失败/跳过即停、可取消、失败原因透传 toast；
  生成入口先 `waitForCanvasRevision`（排空保存队列，非硬门禁）；
- 错误处理：`friendlyGenerationMessage`（短中文保留、长英文/符号替换为友好回退），
  节点错误 + 重试按钮，服务端 `retrySafetyDecision`（安全重试/续跑 Provider 任务）；
- 刷新恢复：`recoverPendingGenerationTask` 按幂等键找回。

### 2.3 结论

1. 我们的生成链路在“防重复付费、刷新恢复、安全重试、额度预检”上比 Unboundry 更重、更稳；
2. 主要差距在体验层：无全局“生成任务”面板、无“轮询失败→点击重试续查”轻恢复、
   错误码未完全结构化（部分路径仍依赖 message 正则）；
3. Unboundry 不存在“平台连接正在更新”类错误，因为并发控制全部在服务端；
   我们此前的锁死锁（同步 SQLite 锁 + await 持锁导致并行提交卡 5s）已另行修复
   （见 `UNBOUNDRY_CANVAS_SAVE_REPLICATION_PLAN_2026-08-06.md` 与本批改动）。
