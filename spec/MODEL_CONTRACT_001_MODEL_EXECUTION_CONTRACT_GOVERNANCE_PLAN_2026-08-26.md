## 1. 结论与问题定义

本任务采用“平台代码提供安全执行能力，管理员配置具体模型合同”的边界。

管理员以后应能自行维护日常变化：模型参数、输入模式、素材角色、每个角色数量与顺序、角色到 Provider 字段的映射、创建/查询接口、任务号、状态、结果、错误和合同版本。只要变化仍落在平台已经支持的协议族、安全转换和节点语义中，不应再改代码或重新发布应用。

但不能把任意 Provider 协议变成可执行脚本。新协议、新鉴权、新模态、新节点行为、秘密处理、网络安全、计费幂等、事务、媒体归属和合规仍由代码控制。

触发本方案的 GK-video-3 问题不是“提示词一定不够强”，而是当前通用媒体适配器把参考素材按猜测式合同提交，不能证明首帧图片被放进 Provider 要求的精确字段。输入没有按合同送达时，继续堆提示词无法可靠保留服装款式。本方案先治理请求合同；即使合同正确，也只能证明素材被正确送达，不能承诺模型一定视觉还原，技术交付与成片质量必须分开验收。

## 2. 目标、非目标与范围

### 2.1 目标

1. 管理员可在后台用结构化表单维护模型能力与执行合同。
2. 每个已发布合同都是不可变、可追溯、可回滚的原子修订。
3. 任务提交前能确定唯一输入模式，完整校验所有角色、数量和字段绑定；歧义、遗漏和多余输入一律阻断。
4. 已受理任务冻结提交时合同，后台改配置或回滚不改变其轮询与结果解析。
5. 新合同可先草稿、静态验证、假 Provider 验证、影响分析和影子比对，再只对新任务启用。
6. 普通用户只看到可理解的中文能力、限制和错误，不接触 JSONPath、哈希或 connector 技术名。

### 2.2 首期覆盖

- Text、Image、Video、Audio 四类生成节点。
- 图片工具调用模型时的源图、参考图、遮罩、扩图准备结果与工具身份输入。
- 已存在的 Provider 身份、模型目录、节点绑定、Generation Task、Provider Attempt、Media publication、ownership 与恢复合同。

### 2.3 首期不覆盖

- Group、Playlist、Storyboard、Probe 等不直接提交 Provider 的节点。
- 任意 JavaScript、模板脚本、循环、函数、环境变量读取、任意 Header/域名或任意 JSONPath。
- 把所有 Provider 差异强行合并成一个万能协议。
- 通用多主结果产品能力。首期通用合同只接收一个主结果；Suno 等既有专用多结果能力必须保持，不得降级。
- 用“请求合同正确”冒充“服装款式、人物、镜头或风格质量通过”。

如果未来 Group、Storyboard 等节点获得自己的 Provider 提交行为，应另建“节点操作合同”，复用本方案的版本、安全、验证和发布基础设施，不把现有生成合同偷偷扩成工作流脚本。

## 3. 核心架构

### 3.1 三层合同与一个原子发布单元

| 层 | 所有者 | 作用 | 是否由管理员日常修改 |
|---|---|---|---|
| 产品能力合同 | 产品/管理员 | 字段、选项、默认值、可见条件、节点能力 | 是；复用并演进 `ModelParameterSchema` |
| Provider connector family | 代码 | 鉴权、网络、安全边界、协议执行、错误分类 | 否 |
| 模型执行合同 | 管理员在代码白名单内 | 输入模式、角色/数量、请求绑定、任务轮询、结果提取 | 是 |
| `ModelReleaseRevision` | 系统原子发布 | 固定前三者的精确组合及审计证据 | 只能新建、发布、回滚，不可原地改 |

首期 connector family 按真实代码边界保留：OpenAI chat/responses、Claude、Gemini、GPT Image、Ark native、Mureka native和代码专用connector。`generic-async-media`只对经过正式证据锁定的GK模型开放；未知协议使用`blocked`发布快照而不是合成可执行合同。R0盘点结果不得被connector名称替代。

### 3.2 `ModelReleaseRevision`

每个发布修订必须原子包含：

- 模型内部 ID、Provider profile 与 Provider model ID；
- capability schema 版本与完整内容；
- execution contract 版本与完整内容；
- connector family 及其代码版本；
- 模式、角色、计数、顺序、绑定、端点、任务/状态/结果/错误合同；
- 官方文档来源及核验日期；
- 编译结果、fixture 集、影响分析、脱敏请求预览；
- 内容哈希、创建人、验证人、发布时间与前序修订。

编辑草稿和发布必须分离。已发布修订不可原地修改；任何变化创建新 revision。发布事务要么完整切换能力合同与执行合同，要么完全不切换，禁止“参数新、执行旧”或反向组合。

### 3.3 生命周期

`DRAFT → VALIDATED → PUBLISHED → RETIRED`

另有紧急状态 `REVOKED_FOR_NEW_SUBMISSIONS`：立即停止新 POST，但已经被 Provider 接收的旧任务仍按冻结合同安全查询；只有端点或凭据本身被判定不安全时才停止旧任务查询。

回滚只改变新任务采用的 active revision，不改变已受理或运行中的任务。

## 4. 输入模式、角色与数量合同

### 4.1 选择规则

- 一个模型可以支持多个素材角色，后台用多选配置能力。
- 一条具体连线或一份具体媒体输入必须且只能选择一个角色，不能同时既是首帧又是参考图。
- 同一角色可以有多份素材，通过 `minItems`、`maxItems`、`ordered` 和 `shape` 表达。
- 多种合法输入组合必须建成互斥的显式模式；运行时必须唯一命中一个模式。零命中或多命中都阻断提交。
- 不允许静默截断、丢弃、重排、把多张偷偷取第一张，或把未知角色降级成普通参考图。

### 4.2 建议结构

每个模式至少包含：

- `modeId`、中文名、适用节点类型；
- Prompt 要求与最终 Prompt 来源规则；
- 可用角色及每个角色的 `minItems/maxItems/ordered/shape`；
- 必填参数与互斥条件；
- 目标 connector family；
- 请求绑定集合；
- 用户侧能力说明和阻断文案。

角色使用稳定机器 ID 和可改显示名。已发布角色 ID 不能删除或复用为新语义；弃用后保留历史显示，并在新提交时给出明确修复提示。

### 4.3 GK-video-3 首个试点的冻结事实

只有已有正式证据支持以下两种模式：

| 模式 | Prompt | 素材角色 | 数量 | Provider 目标 |
|---|---|---|---|---|
| 文生视频 | 必填 | 无 | 0 | 不发送媒体字段 |
| 首帧生视频 | 必填 | `first-frame` | 恰好 1 张图片 | `params.images`，URL 数组 |

创建接口为 `POST /v1/media/generate`；创建响应任务号路径为 `task_id`；状态查询为 `GET /v1/media/status`，查询参数 `task_id`；成功结果地址为 `result_url`。

没有正式证据前，不给 GK-video-3 配置尾帧、多图参考、参考视频、主体图或自动取第一张等能力。管理员界面可以表达这些角色，但本模型不能靠猜测勾选。

## 5. 声明式请求绑定

### 5.1 可用来源

- Provider model ID；
- 节点自身 Prompt、上游文字与按既定规则形成的 final Prompt；
- 已验证的模型参数；
- 按角色分组且已就绪的素材 URL 或 file ID；
- 合同中的固定常量；
- 创建响应中的 task ID。

### 5.2 允许的转换

- 字符串、数字、布尔等基础类型转换；
- 合同明确允许时的 scalar ↔ array；array → scalar 只能显式配置且数量合同已证明恰好一项；
- 枚举映射；
- 空值省略；
- 按合同排序形成数组；
- URL 与 file ID 二选一；
- 简单条件；
- 固定前缀或后缀。

### 5.3 目标范围

目标只能落在 connector family 公开的 JSON、query 或 form 槽位。端点必须是 Provider profile 基址下的受限相对路径。Header、鉴权、域名解析、重定向和出站策略不开放给合同。

### 5.4 明确禁止

- JavaScript、表达式求值器、循环、用户函数或插件代码；
- 读取环境变量、秘密、文件、Cookie 或浏览器状态；
- 任意 Header、完整 URL、域名、端口或代理；
- 任意 JSONPath、递归搜索或“到处猜字段”；
- 未声明输入的透传；
- 出错后自动换字段、换模式或换 Provider。

后台编辑采用“来源 → 转换 → 目标”的结构化行。原始 JSON 只可作为脱敏、只读预览，不作为主要编辑入口。

## 6. 创建、轮询、结果与恢复

### 6.1 创建前

在越过 Provider POST 边界前，系统必须再次核对 active revision、Provider profile、credential revision、模型绑定和编译哈希。任一漂移都阻断提交并重新预检，不能继续使用已失效预览。

### 6.2 创建结果不确定

如果 POST 已发出但响应是否被 Provider 接收无法证明，任务进入 `outcome_unknown`：

- 冻结当次合同、请求身份和恢复证据；
- 禁止重新 POST；
- 只允许在可证明的官方查询/用量恢复路径内核对；
- 无法证明时保持未知，不用退款字段、费用解析或超时猜测触发重试。

### 6.3 Provider 已返回任务号

必须在首次 poll 前原子冻结并绑定：Provider profile、model ID、credential revision、connector family/version、`ModelReleaseRevision`、合同哈希、provider task ID、poll/status/result/error 规则。

后台后续发布或回滚不改变这条任务。服务重启、浏览器刷新和任务恢复只查询原 task ID，不能按新合同重建并重新提交。

### 6.4 状态、结果、错误与取消

- 只解析合同列出的有限路径和枚举映射；未知状态 fail-closed。
- 轮询间隔、总时长、最大请求数、退避和并发受代码硬上限约束，管理员只能在上限内选择。
- 结果 URL 仍经过既有公网 HTTPS、SSRF、资源大小、类型、下载与 publication 安全链。
- 取消只有 connector 已实现且 Provider 正式支持时可配置；否则 UI 不显示伪取消。
- 401/403、429、网络/超时、5xx、格式错误都不能触发端点 fallback。仅在合同显式声明且通常为 404/405 时，才可走预先验证的兼容端点。
- cost/refund/usage 解析仅作审计证据，不直接写产品余额，也不是唯一重试依据。

## 7. 管理员可改与必须改代码的边界

### 7.1 管理员可改

- 模型 ID、展示名、说明、官方文档链接；
- 参数字段、选项、默认值、可见/必填条件；
- 输入模式、角色、数量、顺序和 shape；
- 白名单来源、转换与目标映射；
- connector 允许范围内的相对创建/查询/取消路径；
- task ID、状态、结果、稳定错误码路径和枚举映射；
- 代码硬上限内的轮询窗口；
- fixture、变更说明、版本、发布、回滚和停止新任务。

### 7.2 仍需代码

- 新协议族、鉴权方式、签名算法、流式/回调机制或新模态；
- 新节点语义或新工具操作；
- 密钥加密、SSRF/DNS rebinding、网络/重定向策略和硬大小限制；
- Provider 商业身份与账号凭据隔离；
- 计费幂等、重复提交保护、unknown outcome 与恢复；
- 数据库事务、task/attempt、Media publication、OSS ownership、Canvas 回填；
- 内容合规、可信素材、真人/AI 角色政策；
- 白名单 DSL 不足时新增受审计转换或 connector 能力。

这条边界意味着“管理员可改”不是“管理员能接入任何陌生 API”。如果新模型超出平台语言，系统必须明确提示“需要平台升级”，不能以猜测式配置勉强发布。

## 8. 后台 UI/UX 规范

### 8.1 信息架构

不把本能力继续塞进现有长卡片、弹窗或 `AdminModelParameterEditor`。新增独立“模型合同详情/工作台”页面。

模型列表只展示：Provider、能力类型、合同状态、当前修订、健康状态、受影响模板和新任务可用性。详情按以下区块渐进披露：

1. 基本信息与官方文档；
2. 输入模式；
3. 素材角色与数量；
4. 模型参数；
5. 请求绑定；
6. 任务、状态、结果与错误；
7. 验证与发布；
8. 版本历史、回滚与紧急停止。

桌面可用左侧导航、中央表单、右侧实时摘要；窄屏折叠为单列。右侧摘要不能变成第二套可编辑状态。

### 8.2 操作语义

必须明确分开：

- `保存草稿`
- `本地验证｜不调用 Provider`
- `发布`
- `回滚`
- `停止新任务`

保存草稿必须显式服务端保存；存在未保存修改时离开要警告。任何编辑都会使旧验证结果失效。Enter 不能触发发布。

发布确认必须说明：只影响新任务、运行中任务使用旧修订、受影响模板清单、是否阻断不兼容模板、这一步不会调用 Provider。

### 8.3 并发编辑

合同草稿使用 revision/CAS，不沿用 Canvas 跨标签“最后保存者胜”。发生冲突时提供重新加载、差异查看和复制未保存内容，不能静默覆盖另一位管理员。

### 8.4 视觉与可访问性

- 对齐现有深色灰阶、圆角、按钮高度、自绘灰色选择器、16px checkbox 和 focus 样式；
- 橙色用于警告，红色只用于错误或危险动作，不出现原生蓝色控件；
- 键盘可完整操作；焦点回归正确；模态使用 inert/focus trap；错误与字段关联；状态不能只靠颜色；
- 验证 1280×720、1440×900、1920×1080；宽度 ≤928px 单列；不得横向溢出、裁切、菜单被遮挡或 sticky 操作栏覆盖内容。

## 9. 兼容与模板治理

- 旧节点参数不能被新默认值静默归一化。
- 旧枚举值保留原值并显示“不再受支持”，由用户显式修复。
- 旧角色不能被重映射或删除；保留历史标签并在新生成前友好阻断。
- 发布合同只能检查模板，不能自动改写模板。存在不兼容已发布模板时，必须阻断合同发布，或由独立模板版本/停用流程显式处理。
- 任务快照、历史结果和旧 Canvas 按其原合同可读；只有新提交要求 active contract 合法。
- 普通用户界面用中文说明“缺首帧”“该模型只支持一张首帧”等，不暴露 revision hash、connector、JSON 字段。

## 10. 发布前验证门

### 10.1 静态编译

- 模式互斥且运行时可唯一选择；
- 所有必填参数、角色和计费相关字段均有且只有一个来源；
- 不存在未消费输入、未知角色、超量素材或静默丢弃；
- 目标路径、转换、端点、结果和错误规则均在 connector 白名单；
- 一个发布修订的 capability 与 execution 内容原子一致。

### 10.2 模板兼容

列出所有受影响模板、节点快照和旧枚举/角色。任何不兼容都阻断发布，除非模板已被独立修订或明确停止新使用。

### 10.3 脱敏确定性预览

用固定假 URL/file ID 和假 Prompt 生成确定性请求预览；秘密、Authorization、签名 URL、Cookie、真实用户内容不能出现。相同修订与输入必须产生相同规范请求哈希。

### 10.4 Fake Provider 矩阵

至少覆盖：submit、poll、success、明确 failure、缺 task ID、未知状态、格式异常、超时、取消、401/403、429、5xx、超大资源、恶意 URL、重定向、secret reflection、重启恢复和并发发布漂移。默认不调用真实 Provider；任何付费或真实控制面测试需另行明确授权与预算。

## 11. 分阶段落地

### R0：全量只读盘点

盘点四类生成节点、图片工具、所有已发布模型、Provider profile、connector、参数 schema、输入组装、task/poll/result/error、模板依赖和恢复路径；对照官方文档，把每条模型合同分类为 `EXACT / SPECIALIZED / GENERIC_GUESS / UNKNOWN`，形成影响图。没有 R0 证据不得直接迁移 GK 后猜测其他模型。

### R1：底座，不切运行时

建立合同 schema、编译器、不可变 revision、原子发布、task snapshot 和审计；旧运行时继续工作。先完成 fake 预期红与安全边界。

### R2：后台工作台

实现列表、详情、草稿、CAS、验证、预览、影响分析、发布/回滚/停止新任务和版本历史；不以原始 JSON 作为主要操作方式。

### R3：GK-video-3 小流量试点

只实现本方案冻结的文生视频与单首帧生视频。先对同一输入做旧/新请求的纯本地 shadow compare，不双发 Provider POST；通过后只让 GK 新任务采用新合同。

### R4：其他 relay media

逐模型根据 R0 官方证据迁移。不能按“同一个 `/v1/media/generate`”推断字段相同。

### R5：文字与 GPT Image 协议族

在各自 connector family 内迁移；保留现有 Files API、同步图像、专用尺寸和结果安全边界。

### R6：Ark native 与 Mureka native

只迁移纯声明式差异。原生签名、资产、回调或专用多结果继续留在代码 connector。

### R7：关闭猜测式通用路径

只有全部已发布模型都有 published revision、所有模板兼容、旧任务恢复、紧急停止、回滚、安全测试和独立终审均通过，才关闭旧 generic guessing。不得为赶进度一次性切换全部模型。

当前候选的实现策略是：GK使用唯一代码准入的声明式`generic-async-media`合同；其余有现存专用实现的模型固定为`specialized-code`；`kwvideo-v2`因证据仍为`UNKNOWN`而固定为`blocked`，目录和新任务准入均fail-closed。旧任务仍只按自身冻结快照恢复，不因R7改写。

## 12. 风险、对策与不做的过度设计

| 风险 | 后果 | 对策 |
|---|---|---|
| 管理员错误配置放大 | 大量新任务失败或浪费费用 | 草稿、静态验证、影响分析、canary、紧急停止、回滚 |
| 能力与执行配置漂移 | UI允许但请求没发送 | 原子 `ModelReleaseRevision` |
| 运行中任务合同漂移 | 结果无法找回或重复提交 | task 冻结 revision 与 provider task ID |
| DSL 不断膨胀 | 形成难审计脚本平台 | connector-specific compiler + 有限白名单 |
| SSRF/秘密泄露 | 安全事故 | 域名、鉴权、Header、网络始终代码拥有 |
| 轮询风暴 | Provider 限流与服务负载 | 代码硬上限、并发/退避/总预算 |
| 技术通过被当质量通过 | 服装仍变款却误报成功 | 输入交付、技术结果、用户视觉验收分层 |
| 后台过于复杂 | 管理员误操作 | 独立工作台、渐进披露、结构化绑定、中文摘要 |
| 多管理员覆盖 | 发布错误合同 | 草稿 revision/CAS 与差异恢复 |
| 旧 Canvas/模板漂移 | 历史数据被静默改写 | fail-closed、保留旧值、模板只检查不改写 |

首期不建设任意编程 DSL、通用工作流引擎、插件市场、自动抓取 Provider 文档、AI 自动发布合同或通用多输出编辑器。这些都会扩大安全面和耦合，不是解决当前问题的必要条件。
