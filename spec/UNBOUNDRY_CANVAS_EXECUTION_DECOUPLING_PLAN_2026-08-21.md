## 1. 结论与目标

本轮暂停画布执行链上的功能扩张，采用渐进式解耦，不全面重写画布。

目标是消除以下结构性脆弱点：

1. Text/Image/Video/Audio 节点通过 React 组件 `useEffect` 注册整组执行能力，导致执行生命周期依赖节点是否挂载；
2. React Flow 视口虚拟化与工作流执行耦合，当前需要用渲染层保活节点维持执行；
3. 同一画布仍以“存在任意运行组就拒绝下一组”的方式全局串行；
4. 运行保护过粗，影响生成期间操作无关画布内容的手感；
5. 画布文档、工作流运行、服务端生成任务和临时 UI 状态边界不够清楚；
6. `CanvasSurface.tsx` 承担过多状态、交互、持久化和工作流桥接职责，修改容易产生连锁副作用。

本轮完成后必须达到：执行不依赖节点组件挂载；离屏与卸载不影响运行；无关画布区域不被冻结；非重叠工作流可以并行；重叠工作流在付费提交前被明确阻止；运行、任务和画布结果的所有权可以核对；失败不会静默覆盖或重复提交。

## 3. 权威状态与核心不变量

### 3.1 三类权威状态

1. **CanvasDocument**：正式画布内容，包括节点、位置、连线、配置和已确认结果引用；由画布 revision 保护。
2. **RunState / GenerationTask**：执行事实，包括 runId、taskId、attempt、providerTaskId、checkpoint、锁、重试、核对和终态；服务端任务与有所有权证明的检查点优先。
3. **UiState**：选中、弹窗、面板、拖拽、临时进度动画等；不是任务事实，不得参与付费防重判断。

### 3.2 必须始终成立的不变量

- 一次真实生成提交只有一个权威入口；迁移期不得新旧路径双提交。
- 同一 `accountId + canvasId + runId + nodeId + attempt + inputFingerprint` 不得产生第二个付费提交。
- 节点是否渲染、是否可见、是否被选中，不得决定任务是否存在或是否继续。
- 一轮运行只能释放自己的锁、状态和检查点；不得清空其他轮次。
- 结果回写前必须核对 run、task、目标节点、输入指纹和语义 revision。
- 不能安全回写的结果保留在任务/结果入口，不静默覆盖用户新编辑。
- 已提交任务无法确认时先 exact reconcile，不用重新提交代替核对。
- 画布保存失败不能删除任务事实，也不能触发补偿性重复付费。
- 任何被阻止的用户操作必须有明确、持续可见的原因，不能静默点不动。

## 5. 阶段安排与闸门

阶段顺序不可调换。一个阶段未满足退出条件，不进入下一阶段。

### 阶段 0：基线、合同与测试选择

目标：在不改业务行为的前提下，确认真实调用链、状态所有权和最低验收集。

工作：

- 核对仓库身份、工作树和权威文档；
- 盘点四类节点的注册、预检、提交、轮询、恢复、结果应用和保存链；
- 把现有测试映射到验收矩阵，识别需要新增的最小红测；
- 固定本轮非目标、幂等合同、结果所有权和停止红线；
- 确认同一 HEAD 是否已有可信全量证据，避免重复跑全量。

退出条件：调用链和状态权威无未知关键断点；验收矩阵可以执行；没有基线身份冲突。

### 阶段 1：执行器脱离 React 组件

目标结构：

```text
Canvas node snapshot + graph snapshot + execution context
                         ↓
                 NodeExecutorRegistry
                         ↓
            preflight / run / recover / apply
```

迁移顺序：Text → Image → Audio → Video。每次只迁移一种节点。

要求：

- 执行器不得读取 DOM、组件 ref、选中状态或节点是否可见；
- 执行器通过明确的 snapshot/context 获取节点、上游输入、模型配置、媒体引用、画布 revision 和 task ownership；
- React 节点只负责显示、编辑、触发命令和展示结果；
- 迁移期可以比较纯参数/预检结果，但真实提交入口必须互斥；
- 已提交旧任务必须能被新路径 exact recover，不得重新付费生成代替恢复；
- 每迁移一种节点，先证明新路径，再删除该类型旧 registration；
- 四类全部完成后删除 `waitForRegistrations` 和 execution registrations 的运行依赖。

退出条件：节点完全不挂载时仍能预检、执行和恢复；四类节点不再通过组件 registration 提供工作流执行能力；没有双提交路径。

### 阶段 2：取消执行保活，建立精确交互保护

前提：阶段 1 已证明执行不依赖组件挂载。

工作：

- 删除 `workflowRenderRetention` 和 `workflowRetainedNodeIds` 对执行正确性的依赖；
- 保留正常视口虚拟化；
- 把一个全局 locked 集合改成按 run、节点、字段/操作判断的策略；
- 启动时冻结语义输入快照，不冻结整张画布。

产品规则：

| 操作 | 本轮参与节点 | 无关节点 |
|---|---|---|
| 平移/缩放画布 | 允许 | 允许 |
| 查看/选中 | 允许 | 允许 |
| 移动布局位置 | 原则允许；不得改变语义输入 | 允许 |
| 新增节点 | 允许 | 允许 |
| 修改 Prompt/模型/参数/输入媒体 | 阻止并解释 | 允许 |
| 删除节点 | 阻止并解释 | 允许 |
| 增删运行依赖边 | 阻止并解释 | 允许 |

退出条件：节点离屏/卸载不影响运行；不再需要渲染保活；生成期间无关画布操作正常；运行语义输入仍受保护。

### 阶段 3：多工作流运行协调

目标结构：

```text
Map<runId, RunState>
Map<nodeId, LockOwner>
```

每轮独立拥有 scope、groupId、runId、snapshot、node states、task ownership、checkpoint、locks、stop/failure/final summary。

启动新工作流前计算冲突集合：

- 组内可执行节点；
- 直接和必要的间接语义输入；
- 结果写入目标；
- 会被修改的边和结构；
- 共享可变媒体/配置资源。

规则：

- 语义锁集合无交集：允许并行；
- 只共享已证明不可变的只读资源：可在测试证明后允许；
- 共享可变输入、输出或结构：付费提交前阻止并列出冲突节点；
- 一组完成/失败/停止只能移除自己的 executing id、checkpoint 和锁；
- 并行工作流不等于无限 Provider 并发，继续服从账户、模态、Provider 和服务端队列上限；
- 跨标签仍以可靠租约为最终权威，浏览器内存 Map 不是互斥证明。

退出条件：A/B 非重叠工作流可并行；A 完成/失败/停止时 B 继续；重叠工作流在提交前明确阻止；任务数与预期节点一一对应。

### 阶段 4：状态分层与结果冲突保护

工作：

- 让 UI 运行显示从 RunState/GenerationTask 派生，不把节点 `loading` 当任务事实；
- 明确画布只保存正式内容，运行检查点不混入图结构；
- 结果回写验证 runId、taskId、ownershipKey、inputFingerprint、目标节点和语义 revision；
- 发生冲突时保留结果，提示“节点已变化”，允许用户另建节点或明确应用；
- 保存失败后任务仍可在任务面板核对，不通过重新提交补救；
- schema/文档变化采用加法迁移；遇到未知旧数据拒绝覆盖。

退出条件：刷新/切画布可重建运行事实；旧结果不覆盖新编辑；任务事实不被画布保存清除；保存失败不产生重复提交。

### 阶段 5：只做必要的 CanvasSurface 职责拆分

候选边界：

- CanvasViewportController；
- CanvasSelectionController；
- CanvasDocumentCommands；
- CanvasPersistenceAdapter；
- CanvasInteractionPolicy；
- CanvasWorkflowBridge；
- CanvasNodeRenderer / CanvasEdgeController。

约束：

- 一次只抽一个职责，不同时改变业务行为；
- 先抽纯函数和命令，再抽副作用控制器；
- 渲染层不能提交 Provider；执行层不能操作 React 组件；持久化层不能决定交互权限；UiState 不能决定任务恢复；
- 本阶段可以继续通过现有完整文档保存适配器落盘，不强制同时改为 Patch 协议；
- 退出标准是依赖方向和故障隔离，不是文件行数好看。

退出条件：工作流不直接依赖 React Flow 节点组件；持久化不散落在无关交互回调中；新增/修改一种执行器不再需要进入 CanvasSurface 处理生成细节。

### 阶段 6：最终复核与候选验收

必须覆盖：

- 开始时部分节点离屏；运行中拖出/拖回；
- 运行期间平移、缩放、新增和编辑无关节点；
- 两个非重叠工作流并行；共享输入/输出时冲突阻止；
- A 完成/失败/停止，B 不受影响；
- 刷新、切画布、网络丢响应、任务已提交但结果尚未保存；
- 旧结果遇到节点新编辑；保存 revision 冲突；
- 双击开始和跨标签恢复不重复提交；
- 98/171/200 节点密集画布的视口与交互；
- 错误提示持续可见且指向真实节点/运行，不只靠短 toast。

完成后至少进行三类独立只读复核：状态机/并发、数据/幂等、UX/回归。主 Agent 必须复核子 Agent 证据。

## 6. 风险驱动测试政策

### 6.1 测试节奏

| 时机 | 默认范围 | 目标 |
|---|---|---|
| 小修改 | 类型检查 + 1～3 个最小相关测试 | 约 5 分钟内 |
| 单一节点类型迁移完成 | 该节点的执行、任务、恢复和结果应用领域测试 | 不跑无关领域 |
| 一个架构阶段完成 | 工作流/画布/任务相关中等回归 | 约 15 分钟内 |
| 核心执行器全部迁移完成 | 一次核心架构回归 | 验证跨节点公共边界 |
| 最终候选 | 一次正式安全全量 | 最终回归证据 |

全量测试原则上最多出现在：缺少可信基线时一次、核心执行架构迁移完成后一次、最终候选一次。若相同 HEAD、相同环境已有可信结果，不重复运行。

### 6.2 扩大测试范围的正当理由

只有改动触及以下边界时才扩大：真实提交幂等、generation_tasks 状态机、画布/数据库持久化、retry/reconcile、跨标签租约、多工作流锁、结果 ownership/revision、删除/迁移数据、CanvasSurface 公共交互入口。

“更保险”“改动很多”“顺便跑一下”不是扩大测试的理由。扩大前必须写出风险传播路径。

### 6.3 输出纪律

- 不把大段测试日志写进聊天或 Checkpoint；只记录命令、环境、退出码、通过/失败数和失败名称；
- 失败后先重跑失败项和邻近场景，不立即全量；
- 自动化 PASS 不得升级为 USER PASS；
- 未运行的场景保持 `NOT_RUN`，不得写“理论通过”。

## 7. 风险与应对摘要

| 风险 | 严重度 | 主要应对 |
|---|---|---|
| 新旧路径重复真实提交 | 极高 | 提交入口互斥；服务端幂等；迁移期只比较纯参数 |
| 执行器遗漏组件内部隐式输入 | 高 | 逐节点输入清单；显式 ExecutionContext；按类型迁移 |
| 旧任务无法恢复 | 高 | 先兼容读取/恢复旧任务，再切创建；不得重提代替恢复 |
| 取消保活后隐藏依赖暴露 | 高 | 新执行器稳定后再删除；离屏/卸载红测先行 |
| 锁太少导致输入漂移 | 高 | 启动快照、输入指纹、语义字段锁 |
| 锁太多继续伤害手感 | 中高 | 操作级策略；无关节点完全可用；明确提示 |
| 多轮释放彼此状态 | 极高 | 所有 add/remove/release 按 runId；禁止全局 clear |
| 锁集合漏算导致覆盖 | 极高 | 首版保守；列出冲突资源；专项交叉图测试 |
| 并行放大 Provider 限流/成本 | 高 | 服务端有界并发和 queued；不使用裸无限并发 |
| 旧结果覆盖新编辑 | 极高 | ownership + fingerprint + semantic revision；冲突结果旁路保存 |
| 数据迁移损坏旧画布 | 极高 | 加法迁移；备份；未知格式拒绝覆盖；不做破坏性批量改写 |
| 拆文件但耦合未下降 | 中 | 以依赖方向和接口为退出标准，不以行数为标准 |
| 过度测试消耗时间/Token | 中 | 风险分层、结果复用、限制输出和全量次数 |
| 治理无限扩张 | 高 | 严格非目标；Checkpoint 下一步唯一动作；阶段闸门 |

## 8. 子 Agent 使用规则

- 子 Agent 用于只读调用链审查、并发/状态机反例、测试场景设计和阶段完成后的独立复核；
- 核心代码原则上由主 Agent 修改，避免共享工作区交叉写；
- 子 Agent 默认不得改共享文件，除非主 Agent 分配了互不重叠的明确文件范围；
- 子 Agent 的“通过”只是审查意见，主 Agent必须复核代码、命令和证据；
- 不得用多个 Agent 的相同意见替代运行证据。

## 10. 必须停止的红线

出现任一项，立即保存证据、更新 Checkpoint、停止后续阶段，不得通过继续堆修复掩盖：

- 发现一次重复真实提交；
- 旧结果静默覆盖用户新编辑；
- 已提交任务没有可核对的持久化记录；
- 一轮结束清除了另一轮状态或锁；
- 数据迁移破坏旧画布或媒体；
- 无法判断 Provider 是否已经提交；
- 继续需要删除/手工修改真实数据；
- 只能放宽安全校验才能让测试通过；
- 为完成当前阶段必须同时重写三个以上原本不在范围内的核心模块。

## 11. 完成定义

只有验收矩阵所有 P0 强制项有合格证据、没有 `BLOCKED`、文档与代码一致，并满足以下条件，Goal 才能标记完成：

- 四类节点执行不依赖 React 组件挂载；
- 离屏/卸载不影响执行，执行保活依赖已删除；
- 无关画布操作不被冻结；
- 非重叠工作流可并行，重叠工作流在提交前阻止并解释；
- 每组停止、失败、完成互不干扰；
- 任务可在刷新/切画布后安全核对和恢复；
- 旧结果不静默覆盖新编辑；
- 保存失败和网络丢响应不造成重复提交；
- 风险驱动自动测试、关键零付费浏览器验收和最终安全全量通过；
- `未验证` 仍明确标记，没有被包装成 PASS；
- 三类独立复核完成，主 Agent 已复核证据。

本 Goal 已包含受控真实付费验证和最终发布。用户主观体验确认仍只能由用户给出；Agent 完成真实页面技术验证后状态最高为 `PRODUCTION_PUBLISHED_AGENT_REAL_PAGE_PASS / USER_RECHECK`，不得自行写 `USER_PASS`。
