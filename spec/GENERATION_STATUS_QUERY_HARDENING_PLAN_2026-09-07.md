## 1. 给用户的说明

目标：生成过程中，网页偶尔查不到进度时，先自动重新查询同一项任务，减少手动点击“重新检查”。

推荐第一步只做“有限次数的自动重查”。第一次和第二次暂时查询失败后，分别等待1秒、2秒重查；第三次连续失败才保留现有的手动检查入口。只查原任务，不重新生成，不因此再次调用收费接口。网络长期不通仍会暂停，不能承诺所有异常都能自动恢复。

没有证据证明现有任务系统需要推倒重写，也没有把这次静态发现认定为已复现的线上故障。上一轮已验收修复保持完成；本方案是新一轮体验加固候选。

## 3. 首批候选设计：原任务的有限自动重查

### 3.1 允许重查的范围

- 仅作用于`waitForGenerationTaskWithPause`进入的单节点观察链：公共浏览器端口，以及仍调用该包装器的图片/视频/音频/文字兼容路径。已静态核实四类节点都构造`createBrowserSingleNodeGenerationTaskPort`；[文字节点](../client/src/canvas/TextNode.tsx)的`finishTextTask`也直接调用WithPause。每种节点的实际使用路径须分别做定向验收，不能用一种节点通过代替四种。
- 自动重查分支只重复原`GET /api/generation-tasks/{taskId}`，保持当前账号、画布、节点、任务、输入/模型合同身份和fixture范围。该分支不持有或重新获取Canvas admission，不得调用生成POST、任务重试/核对写接口、DELETE、Provider提交或新增画布保存；用户主动取消等原有动作仍按其现有合同执行。
- 在`waitForGenerationTask`中增加可选的窄查询重查策略，由`taskPolling.ts`传入；默认不启用，保留工作流直接调用者的原行为。错误判断从上层传入或在既有下层模块定义，不能反向导入`taskPolling.ts`造成循环依赖。
- 重查包住一次GET，不能反复重启整个等待函数；正常查询间隔、原外层循环上限和结束后的恢复入口继续有效。

### 3.2 错误、次数与等待

| 查询结果 | 处理 |
| --- | --- |
| 确认的网络请求失败、状态读取10秒超时、HTTP 5xx | 本观察会话连续失败计数加1；第1次后等1秒，第2次后等2秒，第3次停止自动查询，通知暂停一次并保留taskId |
| 成功返回合法、仍属于当前任务的状态 | 计数归零；进行中按原间隔继续，终态交给现有生命周期处理 |
| 用户取消、组件卸载、账号/画布/节点/任务身份切换导致Abort | 立即停止请求与等待，不提示查询失败，不再发后续请求 |
| 401/403/404及其他非5xx HTTP错误（含429） | 不进入自动重查；沿用对应授权/缺失/限流等提示与安全恢复规则，不标记服务端任务失败 |
| 200但JSON/结果格式无效，或程序处理异常 | 不把它伪装成网络错误循环重试；保留原任务并报可定位的读取/处理问题，不新增生成请求 |
| task本身返回failed或未知付费结果 | 按现有任务结果与重试许可处理；不能把业务失败当成查询传输失败重查三次，更不能借此重新生成 |

在状态GET读取边界区分“fetch传输失败”和“JSON/处理失败”。HTTP状态应在解析错误页之前保留：502/503返回HTML也应判为暂时查询失败；401/403/404即使不是JSON也不能被误判为网络失败。该修正仅限状态读取路径，不改变生成提交/重试等写请求的解析和次数。不能沿用“任意未知Error都可自动重查”的宽泛判断。

同一次观察只允许一个未完成GET或等待计时器；前一次请求完成/中止后才能开始下一次。每次等待和请求都响应同一个调用方AbortSignal，并在开始前、结果应用前验证会话仍有效。迟到结果不能覆盖新节点、切换后的画布或新任务；其他节点的计数和查询不受影响。跨标签查询合并不属于本批。

第3次失败后的手动“重新检查”建立新的有限查询会话、计数从0开始；沿用已有按钮互斥，双击不能生成两套并行观察。暂停不清除任务或生成意图，不修改服务端task.state。重新检查恢复成功后仍由原结果应用链自动回填。

### 3.3 用户界面与既有合同

前两次暂时失败不增加红色“生成失败”提示、不闪烁切换失败态，保持已有进行中表现。第3次失败沿用现有查询暂停提示与“重新检查任务状态”按钮，不新增模态框/倒计时/全局通知。兼容 [UI合同5.9](UNBOUNDRY_UI_DESIGN_SYSTEM.md#59-provider-错误提示) 与第9节的交互规则。

## 4. 批量查询：先测量，暂不实施

当前代码逐任务查询，不代表已经造成瓶颈。后续若授权测量，使用合成1/5/20个并行任务，记录同条件的前端GET数量、峰值并发、状态可见延迟和失败后的操作次数，再判断是否值得新增聚合。

浏览器向我们自己的服务端批量读取任务快照，与服务器向Provider批量查任务是两个不同问题。前者可以聚合读取本地持久任务状态，不以Provider提供批量API为前提；后者必须单独核对各Provider能力、频率、权限和付费边界。任何聚合都须保留逐项错误/缺失、归属校验、结果身份和单任务隔离，不能根据材料假定已有`final_task_id`协议。

本批不预设Redis、PostgreSQL、新队列、任务表、schema迁移或第二套状态机；没有测量证据就不实施批量化。

### 7.1 风险与停止条件

| 风险或可观察到的触发条件 | 处置与判据 |
| --- | --- |
| 自动重查导致任意新增生成/重试/Provider提交、任务身份重建或额外画布写入 | 立即停止该候选的验收或发布，保留请求与身份记录；按7.3撤销该功能。与合法手动动作/服务端投影分开计数，不能靠删除任务或再生成来修复。若真实付费结果不明，继续沿用未知结果保护，先查原任务 |
| 观察会话取消/切换后仍新发GET、保留活动计时器或应用迟到结果；结果写到错误账号、画布或节点 | 立即停止该候选，隔离受影响的浏览器观察链，按7.3撤销；已发出的GET在服务端结束不等于新发请求。不能把已有错误结果自动复制到另一画布，也不能为“清理”批量取消服务端任务 |
| 同一观察链出现两个在途GET；第三次连续暂时失败后仍自动查询；双击开启重复观察 | 视为请求数量或生命周期回归，暂停该候选；记录每个观察会话的请求次数、最大在途数和Abort后请求数，撤销后按RB01/RB02复查 |
| 四类节点、工作流直接等待、原任务找回、手动重新检查或结果回填出现可归因的新回归 | 对应Q用例失败即不交付；共享读取解析有问题时须完整撤销本项读取改动，不能只关闭重查次数后宣布回退成功 |
| 持续网络故障，或账号无权访问、任务不存在、限流、无效JSON | 先按3.2处理。符合约定的三次暂停、授权/格式错误提示本身不是回退理由；仅因服务不可用不触发自动重新生成或服务器版本回退 |
| 长故障的暂停提示比旧版出现更晚；多人/多节点同时失败时GET变多 | 这是有限自动重查的已知代价。单会话每轮失败最多3次GET；若每次均耗尽10秒超时，名义等待约33秒（30秒请求加1/2秒退避），不是浏览器后台节流下的硬墙钟承诺。前台合成超时用例与多节点计数须符合预算；未过验收或等待体验被用户否决时不启用。跨节点/跨标签不宣称已有合并或全局限流 |

同一任务的已受理生成可继续在服务端完成。停止本地观察、撤销客户端代码或切换产品包均不等于取消该生成；已有taskId、尝试、发布结果及画布绑定必须保留。真实事件须先按请求时间和身份区分客户端、服务端、网络与Provider原因；证据不明时停止扩大操作，不凭“页面报错”修改任务终态。

### 7.2 实现前冻结撤销依据

下一次获准本地实现后，先在当前任务记录：实际代码根、分支、完整HEAD、原有dirty文件清单、受影响模块/代码块及合成测试基线。首选范围仍是`taskPolling.ts`与`generationTasks.ts`的状态GET/等待路径及受影响测试；如扩大范围，先补齐对应撤销项。

对准备修改的普通源码逐项保留可恢复的基线内容和差异，先排除两份永久保护JSON与真实数据；若工作树原本有用户修改，基线须包含这些合法修改。用本轮私有本地证据保存必要源码补丁，不用整个真实工作区/数据库快照来代替代码基线，不因本节自动提交Git。已授权提交时将本功能增量保持可识别，记录精确提交；Git历史只用于源码恢复，不是任务/素材备份。

将新增查询策略的启用点、计时器和Abort所有者列清。第3.1的“可选策略”只是代码参数，不是已存在的线上开关；本批不新增后台配置中心。完整撤销集合应包含策略启用、重查循环、HTTP状态/解析分类以及本项新增的调用点；只不传策略不能保证撤回共享GET解析的回归。

### 7.3 本地撤销的操作顺序

1. 记录触发用例、当前候选身份和各类请求计数，停止继续验收该候选。停止由本轮创建的合成场景或卸载其页面以结束客户端观察；不要点击业务“取消生成”来代替停止观察，不批量终止用户浏览器或其他任务。
2. 对照7.2冻结的差异，仅将本功能涉及的代码块恢复到实现前行为，包括共享状态GET读取的修改。保留用户原有及其他任务修改；有重叠时逐块合并、重新审查，不能用`reset --hard`、`clean`或整目录覆盖。撤销受阻时保持本地不交付，不升级成生产操作。
3. 恢复原有“一次暂时查询失败即暂停并保留原任务、手动重新检查”的查询路径；恢复原请求超时、取消与终态处理。保留新策略失败证据和撤销验收用例；新策略用例在撤销候选下标为未启用/预期不适用，不能删掉安全断言来取得通过。
4. 用当前安全入口重新构建受影响本地候选，只重启本轮拥有的临时测试服务；先妥善保留合成画布状态，再重新打开页面或按正常生命周期卸载旧客户端。核对页面实际加载的是撤销后的构建；只改源码/HMR并不证明已有观察链被清理，不能假定旧标签已经换版。
5. 在同一套合成任务和隔离数据上按7.5验证：原任务仍可找回、成功结果可回填、暂停后能手动检查，无新增生成/Provider调用、无迟到写入。允许已有服务端任务自然推进，不能要求运行中数据库整体哈希不变；比较任务身份、既有终态/素材绑定及按原合同允许的变更。
6. 验证通过后记录撤销后的源码/构建身份和结果，保留问题候选及证据；本功能记为已撤销/待修复。重新启用前修复原因并重跑失败用例及受影响回归，再经独立复审和用户验收。未通过时保持不交付，不自动反复切换。

### 7.4 未来上线后的回退准备

本方案审查时尚无产品发布授权与新包；本次实际授权与候选以[当前任务](../TASKS.md)为准。下面必填身份须在候选实际存在时写入当次发布回执；缺任一关键身份或演练结果就不允许上线，不能预填虚构版本或套用旧v0.7.15→v0.7.14演练。

- **新包**：完整commit/tree、版本、构建清单、不可变release路径和当次CI；**回退包**：上线前实际运行且确认兼容的完整身份、构建清单与路径。若以后新包混入其他功能，先证明退回旧包不会撤掉必需安全修复或破坏数据；否则准备经过验证的兼容回退候选，不盲切历史包。
- **数据与执行状态**：本功能不得新增持久字段、schema或迁移。仍须按 [发布手册的备份门与切换回退](../RELEASE_RUNBOOK.md#6-切换与回退) 核对当次备份/恢复证据、当前数据兼容性、受理中的任务与Provider边界；schema没变不能代替兼容测试。不回滚数据库、删除任务/素材/发布记录，不改变未知付费结果保护。
- **当次操作单**：绑定上述精确身份，填写维护/排空、切换、恢复及中止命令与各自期望输出，附实际使用脚本的哈希和审查记录；这里只定义顺序，不借用历史脚本名充当可执行操作单。上线授权中同时明确本次失败处置的范围；已覆盖则不重复问，缺失或风险扩大时只停止未授权动作。

7.1的严重边界回归或已归因于新候选的功能回归构成回退触发；普通网络中断不自动触发。获授权后按已核验的当次操作单执行：保留事件证据和原current → 按既有维护流程阻止新受理并排空/接管在途任务 → 最新一致备份及恢复核验 → 原子切换到精确回退包并按既有服务流程启动 → 核对产品身份、服务、静态资源和原任务恢复 → 确认客户端也已加载回退构建 → 受影响行为验证通过后解除维护。在途请求无法安全排空/持久接管，或身份/备份不符时，不强杀正在提交的任务，不重复POST；保留状态，停止切换并按既有恢复合同处置。已经持久记录为未知付费结果的任务，只能在证明回退包继续保留该保护和原身份后按已审方式接管，不能为完成排空将其标失败或重提。

浏览器中已加载的新代码不会随服务器指针自动撤回。实际发布演练必须覆盖更新/重新打开后的构建身份、草稿保留和原任务找回；不能强制刷新丢掉未保存内容，也不能将旧标签仍在查询误记为回退成功。回退验证失败时维持已授权的维护保护并保存失败证据，不自动再切回问题新包或尝试更老版本。真实systemd切换与隔离Linux兼容演练分别标记；当前二者均未为本功能执行。
